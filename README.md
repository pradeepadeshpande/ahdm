# AHDM: Adaptive Hybrid Detection Model Private Anomaly Detection in Cloud
Code, experiment protocol and computed results accompanying the manuscript

**Author:** Pradeep Deshpande  
**Affiliation / contact:** BLDEA's V. P. Dr. P. G. Halakatti College of Engineering and Technology, Vijayapur, Karnataka, India

1. Description

AHDM detects anomalies in log-derived feature data while protecting the data with
differential privacy (local Laplace perturbation). It combines:

1. **Isolation Forest** anomaly scores,
2. **Denoising Autoencoder (DAE)** reconstruction-error scores,
3. a **logistic-regression meta-learner** that learns the fusion weight between the two
   scores from a labelled validation split.

This repository contains the full implementation, the experiment runner, the figure
generator, and the results (CSV files and figures) that were produced by running the code.
**Every number and figure is computed by the code; no result values are typed in.**

The data are **not redistributed** here. Download them from the original sources and place
them in `data/` (see Section 5).

| Dataset | Source | Files used | Unit of analysis | Size used in `results/` | Anomalies |
|---|---|---|---|---|---|
| Synthetic | generated by `loaders.generate_synthetic` (seed 42) | none | session | 5,000 sessions, 8 features | 565 (11.3 %) |
| OpenStack | Loghub, Zenodo record 3227177 (`OpenStack.tar.gz`) | `openstack_normal1.log` (52,312 lines), `openstack_normal2_4.log` (137,074 lines), `openstack_abnormal.log` (18,434 lines) | VM instance | 2,069 instances | 198 (9.6 %) |
| BGL | Loghub (https://github.com/logpai/loghub) | `BGL_2k_log_structured.csv` (Loghub 2k sample) | log line | 2,000 lines, 10 features | 143 (7.1 %) |
| Thunderbird | Loghub, Zenodo record 3227177 (`Thunderbird.tar.gz`) | a contiguous slice of the full log (see below) | log line | 20,000 lines (stratified subsample of a 200,000-line slice), 11 features | 881 (4.4 %) |

How labels are obtained 

* **OpenStack.** The public data contain no per-VM ground-truth labels. VM instances
  (identified by the `[instance: <uuid>]` tag in log lines) that occur in the
  failure-injection run (`openstack_abnormal.log`) are labelled anomalous; instances from the
  normal runs are labelled normal. These are therefore **run-level labels, not verified
  per-VM failures**. Lines without an instance id belong to no instance and are not used. One
  instance id appears in both normal files and is merged. Timestamps are **not** used as
  features, because the abnormal run (14 May) and the normal runs (16-17 May) were collected
  on different dates, which would otherwise let a model identify the run instead of the
  anomaly.
* **BGL.** A line is anomalous if its alert tag (first field of the raw line / `Label` column)
  is not `-` (Loghub / original BGL convention). Only the 2,000-line Loghub sample is used in
  `results/`; it is not the full BGL log.
* **Thunderbird.** Same alert-tag convention. The public 2,000-line Loghub sample contains
  **no** alert lines (all tags are `-`, spanning 871 s) and cannot be evaluated; the loader
  refuses to run on it. A labelled slice of the full log is required. The slice prepared by the
  authors for the Thunderbird experiments is lines 201,000,000 to 201,199,999 of the full log
  (offset 201,000,000, 200,000 lines, 8,807 alert lines = 4.40 %), selected because it contains
  alerts and **not** as a random sample of the log. For the experiments it is reduced to a
  seeded, stratified random subsample of 20,000 lines (`--max-rows 20000`; 881 alerts, 4.4 %,
  split 12,000 / 4,000 / 4,000 for train / validation / test). Its results are in
  `results_thunderbird/` and, merged with the other datasets, in `results_combined/`.
* **Synthetic.** Anomalous sessions have larger transaction amounts, longer sessions and bursty
  access counts than normal sessions (see `generate_synthetic`).

 Features

Feature definitions and the privacy sensitivity class (HIGH / MODERATE / LOW) of each feature
are in `loaders.py` (`schema` dictionaries). Features that are constant in a training split are
dropped automatically; in the saved run (seed 0) OpenStack used 10 of its 13 candidate features.
BGL and Thunderbird use a *template rarity* feature that is computed from training-split
counts only.

5. Usage Instructions

**1. Get the data** and place these files in `data/`:

* OpenStack: extract `OpenStack.tar.gz` from https://zenodo.org/records/3227177 and copy
  `openstack_normal1.log`, `openstack_normal2_4.log`, `openstack_abnormal.log`.
* BGL: `BGL_2k_log_structured.csv` from Loghub (a raw `BGL.log` or a full structured CSV also
  works; the first file matching `BGL*` is used).
* Thunderbird (optional): download `Thunderbird.tar.gz` from the same Zenodo record, extract it,
  then survey it and extract a contiguous slice:
  ```
  python make_thunderbird_slice.py report  Thunderbird.log --block 1000000
  python make_thunderbird_slice.py extract Thunderbird.log --start 201000000 --lines 200000 --out data/Thunderbird_slice.log
  ```
  Keep only the slice (not the full log) in `data/`.

**2. Run the experiments** (synthetic + OpenStack + BGL; about 11 minutes on one CPU core
in the saved run):

```
python run_experiments.py --data-dir data --datasets synthetic openstack bgl \
    --epsilons 0.5 1 2 5 10 inf --seeds 8 --out results
```
Thunderbird (separate output folder; `--max-rows` is needed because OCSVM and LOF do not scale to >100k rows):

```
python run_experiments.py --data-dir data --datasets thunderbird \
    --epsilons 0.5 1 2 5 10 inf --seeds 8 --max-rows 20000 --out results_thunderbird
```

**3. Combine the runs (all four datasets together):**

```
python combine_results.py --inputs results results_thunderbird --out results_combined
```

This concatenates the per-run rows and recomputes `summary.csv` and `significance.csv`
(nothing is re-run). It warns if the runs differ in seeds, epsilon grid or backend.

**Ablation study** (synthetic, OpenStack, BGL; Thunderbird separately):

```
python run_ablation.py --data-dir data --datasets synthetic openstack bgl \
    --epsilons 0.5 1 2 5 10 inf --seeds 8 --out results_ablation
python run_ablation.py --data-dir data --datasets thunderbird --max-rows 20000 \
    --epsilons 0.5 1 2 5 10 inf --seeds 8 --out results_ablation_thunderbird
```

Outputs: `ablation_long.csv`, `ablation_summary.csv`, `ablation_significance.csv`, `ablation_metadata.json`.
Configurations: A1 IF only; A2 DAE only; A3 equal-weight fusion; A4 AHDM with a fixed threshold T = 0.5; A5a uniform epsilon (every attribute gets the base epsilon; per-record loss differs from A6); A5b uniform epsilon matched to A6's per-record total; A6 full AHDM. A6, A1, A2 and A3 reproduce the main results exactly (max abs difference < 1e-15). The saved ablation results (`results_ablation/`) were produced with PyTorch 2.15.0 (CPU), Python 3.12.3; the Thunderbird ablation is not included and must be run separately.

**4. Build figures and tables** (use `results_combined` for all four datasets):

```
python make_figures.py --results results_combined --eps 1.0
```

**5. Outputs** (in the `--out` folder):

| File | Content |
| `metrics_long.csv` | one row per dataset x epsilon x seed x method: accuracy, precision, recall, F1, AUC-ROC, average precision, fusion weight `alpha`, per-record epsilon `record_epsilon`, DAE backend |
| `summary.csv` | mean and standard deviation over seeds |
| `significance.csv` | paired Wilcoxon signed-rank tests, AHDM vs each other method (AUC-ROC and F1) |
| `run_metadata.json` | library versions, seeds, dataset sizes, features used, runtime |
| `test_scores_seed0.npz` | test-set scores of seed 0 (used for ROC/PR curves) |
| `results_tables.md`, `fig_*.png/pdf` | tables and figures produced by `make_figures.py` |

## 6. Methodology

**Data splitting.** For every seed (0-7) the data are split with a stratified 60/20/20 train/validation/test split. MinMax scaling is fitted on the training split only; validation and test values are clipped to [0, 1]. Rarity features use training counts only.

**Differential privacy.** Local Laplace perturbation is applied to every attribute of every split (train, validation, test). Values are in [0, 1], and these bounds are treated as public, so the sensitivity of each attribute is 1. The base epsilon is scaled per attribute by its sensitivity class: HIGH x0.5, MODERATE x1.0, LOW x2.0 (all attributes are perturbed, including LOW ones). Perturbed values are clipped to [0, 1] (post-processing). A record releases all of its attributes, so by sequential composition its privacy loss is the **sum of its attribute epsilons** (reported in `record_epsilon`; at base epsilon 1 this is 9.5 to 13 for the three datasets in `results/`). The base epsilon is therefore not the total per-record budget. The setting `inf` means no perturbation.

**Models.**
* Isolation Forest (scikit-learn, 100 trees).
* Local Outlier Factor (20 neighbours, novelty mode) and One-Class SVM (RBF kernel, `nu=0.1`,
  `gamma="scale"`) as baselines.
* DAE: d -> 128 -> 64 -> 32 -> 64 -> 128 -> d, BatchNorm and dropout 0.1 in the encoder, sigmoid
  output; Gaussian input noise factor 0.1; Adam (learning rate 1e-3), batch size 64, at most 50
  epochs with early stopping (patience 10) on validation reconstruction loss (no labels).
* AHDM: Isolation Forest and DAE are trained on the noisy training split without labels. Their
  scores are MinMax-normalised and fused as `alpha * s_IF + (1 - alpha) * s_AE`. `alpha` comes
  from the (non-negative) coefficients of a logistic regression fitted on the validation scores
  and labels.
* Component comparisons reported alongside: *DAE-only* and *AHDM-fixed* (`alpha = 0.5`); the full ablation (fixed threshold, uniform epsilon allocation) is in `run_ablation.py`.

**Evaluation protocol (identical for all detectors).** The operating threshold of every method
is chosen on the validation split to maximise F1; the test split is never used for tuning. AUC-ROC
and average precision (threshold-free) are the primary metrics; accuracy, precision, recall and F1
are computed at the validation-tuned threshold. Results are mean and standard deviation over 8
seeds. Significance: paired Wilcoxon signed-rank test across seeds (with 8 seeds the smallest
possible two-sided p-value is about 0.0078); no multiple-comparison correction is applied.

7. Results and reproducibility

All results are in `results/` (synthetic, OpenStack, BGL), `results_thunderbird/` (Thunderbird)
and `results_combined/` (all four datasets: `summary.csv`, `significance.csv`,
`results_tables.md`, figures). Numeric tables are not repeated in this README to avoid
inconsistencies. One summary of the saved results, computed from `results_combined/summary.csv`
and `significance.csv`: across the 24 dataset x epsilon cells, AHDM's mean AUC-ROC differs from
that of Isolation Forest by at most 0.019, and the paired tests (`significance.csv`) show
significant differences (p < 0.05) in only a few cells, in both directions. Random seeds are fixed (split and model seeds follow the
seed index; the synthetic data use seed 42; the `--max-rows` subsample uses a fixed seed).
Re-running with the same library versions on the same hardware should reproduce the numbers;
small differences may occur across platforms.

8. Limitations
* OpenStack labels are run-level, not verified per-VM ground truth; the abnormal run was recorded
  on a different date from the normal runs.
* BGL results use the 2,000-line Loghub sample, not the full log. The Thunderbird slice was chosen
  because it contains alerts, and is not a random sample of the full log.
* Splits are random stratified splits, not chronological. Log data contain many near-duplicate
  lines, so a chronological split could give lower scores.
* Categorical fields (component, node) are ordinal-coded. DAE and baseline hyper-parameters are
  fixed and not tuned.
* Thunderbird: with no DP, the DAE-only score is inversely related to the labels (mean AUC-ROC
  0.088 in `summary.csv`), and the no-DP F1/recall values of several methods are affected by tied
  scores on heavily duplicated log lines. These no-DP Thunderbird values should be interpreted
  with caution.
* Because the per-record privacy loss is the sum over attributes, strong per-record guarantees
  are obtained only at small base epsilon, where detection performance is low; see `results/`.
